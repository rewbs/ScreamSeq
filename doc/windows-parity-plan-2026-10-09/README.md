# ScreamSeq Windows parity implementation plan

Planning baseline: **main `ffe81aa4bfa83bc89b1e1dd92db06c67819c247a`**, rechecked against the remote on 9 October 2026. Status: proposal for review. This review pass changes planning documents only; it does not authorize or execute implementation, application launches, builds or tests. Existing branch work is distinguished from main below.

The recommended first implementation batch is **P0a: restore both platform builds and preserve both kinds of retained recording take**. Existing CI logs at the exact baseline confirm a duplicate Windows member definition and a Mac standard-library/toolchain incompatibility. Follow this with focused data-safety and conformance work, then the native multi-bus Mixer as the first substantial feature batch. Named/grouped note tracks, connected editor ergonomics, remaining file/transport/API workflows and device qualification follow. Windows already implements much of the underlying musical functionality; shared extraction should preserve that working infrastructure and its retained-state protections.

Parity means equivalent musical results, reversibility, persistence, discoverability and composing efficiency. It does not require identical controls, window decorations or modifier keys. Both native applications continue to build from **one main branch**. No JUCE, common UI shell or third-party cross-platform audio framework is proposed.

### Routing, plugins and transport

**Mixer gap:** `MixerEditor.inc::installMixerControls/layoutMixerControls` creates a selected-bus list and numeric fields with Apply; no simultaneous strip owner exists on main. `MixerOperations::invoke` already supports `mixer.bus.set(preview:true)` for live gain/balance/width/mute/solo frames without history. `mixer.meters` and shared rendering already exist. Build strips around these capabilities; preserve the current Details/Routing editors.

**Graph functionality exists:** song-root and recipe editing, groups, insert/detach/heal, note routes, presentation metadata, trims/inverse compensation, fan-out, seven source kinds, scope/listen and provenance span `GraphWorkflow*`, `GraphEditor`, `SongRoutingWindow`, `GraphTrimsWindow`, `SignalObservation` and Session operations. Mac references 29–34, 47–49, 54–57 and the 126 graph command entries are acceptance inputs. Source-backed operations accessed through forms are an ergonomic difference, not proof of missing DSP. Several direct Mac canvas actions need a native contextual counterpart and explicit command registration.

**Current live boundary:** Windows worker preparation plus UI producer identity/epoch checks admit supported graph controls, routing, scratch and rack changes before history commit. `HostedProjectPlayback::prepareNativeUpdate` explicitly rejects changes to renderer schedule/identity fields including `noteTracks` and `columnMutes`; those need a new narrow publication contract. Shared host supports compatible effect-preset replacement; instrument preset held-voice replacement remains a stopped operation. Check these exact paths at runtime rather than perpetuating stopped-only claims. Union cycles, incompatible latency/layout, unavailable plugins and exhausted budgets must reject before audible plan/history changes.

Graph limits shared with Mac remain explicit: channel/bus fan-out taps after inserts; individual reusable-copy external Main routing belongs to its assigned stage; a song-root follower has one analysis tap (use a bus for a sum). Aggregate stage telemetry must not masquerade as a selected processor copy. General zero-delay feedback and arbitrary unsupported live edits are not parity requirements.

**Plugin parity:** all 15 reference built-ins use shared `NativeEffects`, with Windows generic parameter pages, programs, buses, aliases, presets, browser, missing-location repair and VST3 HWND hosting already present. AU execution remains Mac-only; Windows must retain its opaque state and identify unavailability. Do not rename class/instance/parameter identities or substitute plugins by display name. Broader installed-plugin behavior and architecture matching are qualification questions.

**Transport/API gaps:** Windows `transport.play` accepts region and loop settings, and `transport.get` reports them, but no `transport.loop` dispatcher for changing an active region was found. Mac's `pattern.timeline.get`/`workspace.ruler` are absent; add engine-derived first-visit times, not fixed-BPM approximations. `graph.controller` is absent as a public Windows method even though native MIDI CC delivery exists. `plugin.meters` needs a compatible projection over existing observation, while `plugin.locations.get/trust` need documented platform semantics over the Windows path/scan/hash workflow. These are method-contract gaps, not blanket absence of looping, metering, MIDI or plugin repair.

### Files, persistence and failures

**Observed:** Windows has atomic native save, preservation-aware binary plist handling, unified chronological history across document/plugin domains, take review, recovery snapshots/browser, dirty-close protections and imported-format support. Current canonical format remains outer **6**, metadata **17**. User file opening uses best-effort recovery (`NativeProjectRecovery.inc`, `ProjectLoadRecovery.hpp`); strict byte decoding remains appropriate for validated internal recovery snapshots. Lossy/converting imports protect the original, including path aliases. Unknown/inert fragments and unavailable plugins must survive wherever current preservation rules retain them.

**Gaps:** there is no Windows `document.exportModule` operation or corresponding user-facing module/audio export command found. Main contains offline diagnostic render modes and selection-to-sample rendering, which are useful infrastructure but do not implement the save-panel workflow in 42/58. Explicit New/Open Demo commands equivalent to the Mac File entries were also not found in the Windows command/controller paths; startup’s demo does not cover replacing a dirty document. Add them through the existing protected document-replacement boundary. ## Proposed shared and native architecture

### Keep the existing successful separation

`TrackerEditor`/`TrackerHosted` already share the engine, NativeSong, document transactions, built-ins, scheduling, routing, plugin facade, automation and prepared transitions. Historical `mac/Audio/NativeInstrument.cpp`, `NativeSignalGraph.cpp`, `PatternCommandRuntime.cpp`, `PatternPitchRuntime.cpp` and `PluginAssignments.cpp` are compiled into the shared hosted target; their directory name does not make them duplicated Mac implementations. A later mechanical move may clarify ownership, but do not combine it with behavioral changes.

Native boundaries remain AppKit/Metal/Core Audio/CoreMIDI/AU on Mac and Win32/Direct2D/DirectWrite/DXGI/WASAPI/WinMM/COM on Windows. Native file dialogs, focus, IME, clipboard ownership, accessibility providers, window placement, notification registration, VST3 view embedding and filesystem atomic replacement remain platform adapters. `PluginBackend` remains the shared provider contract. No document, JSON parsing, layout or vendor discovery enters the audio callback.

### Common edit transaction contract

1. Capture stable document/entity identity, relevant revisions and draft generation. Read immutable model/catalogues; capture raw UI text independently.
2. Parse and validate the complete request, format limits, references, link constraints and budgets. Build a candidate off the audio thread. Dry-run consumes no live IDs/history and cannot stop playback.
3. Classify no-op, control-only, live-preparable or stopped-only change. Reserve history/cache/publication capacity before durable mutation. A unsupported live request reports why and preserves current playback; the user may deliberately retry stopped.
4. Recheck identity/revision/engine epoch at admission. Publish a prepared plan through the existing bounded single-producer handoff and adopt no-throw history/model state according to current staging rules. Retire prior objects on the control owner.
5. Report committed revision and requested/rendered/failed status. Only clear the submitted draft generation; newer typing survives. A transport timeout after the request began is uncertain, requiring a read before retry, not automatic rollback/replay.

For drag previews, reserve a single owner within the UI and keep durable baseline distinct from auditioned controls. End creates one Undo; cancellation restores **current accepted saved controls**, never an old baseline over a newer edit. Document replacement/deletion/epoch change retires the captured gesture. The existing API's preview frame is not per-client isolation; document this and consider a bounded preview lease only if multi-client audition is required, rather than silently changing the public contract.

## Windows visual and interaction principles

The Mac gallery succeeds through a dominant pattern surface, compact contextual inspectors, restrained accent colors, explicit targets, multi-bus Mixer strips and connected navigation. Its native macOS title bars, SF typography, rounded treatments, Command glyphs and capture indicator are not design requirements. Some Mac screenshots also have dense small text and long control lists; copy the useful hierarchy, not every density choice.

Observed Windows composites already have a coherent dark Win32/Direct2D identity and readable Segoe UI/Consolas separation. The shortcomings are primarily organization and interaction: UUID-heavy selectors, large empty form regions, competing generic buttons, fixed strip/inspector minima, and graph text colliding with contained cards. These observations apply to the inspected historical captures; current foreground judgment remains A16.

Proposed implementation rules:

- Use Segoe UI/system UI font metrics for interface text and a readable monospace font for tracker data, time and aligned values. Define shared Windows spacing/type/color tokens around the existing `NativeControls` and `RenderSurface`; preserve native focus rectangles, selection conventions and high-contrast colors. Do not hard-code pixel sizes after DPI conversion.
- Use compact label/control grids with clear section headings, 4/8/12-DIP spacing steps and a consistent primary action area. Treat these as design starting points, then review actual screenshots at each supported scale. Do not make every action a full-width button or force long helper text to determine window width.
- Show names first: `Pulse / Persistent / Gain processor / Gain` instead of a full UUID. Put stable identity and role details in secondary text, tooltip, copy-details command and UIA description. Ambiguous duplicate names must remain distinguishable.
- Keep visible numeric values with units beside faders. Mixer shows several buses with independent fader/meter/mute/solo, horizontal scroll and clear Track/Group/Return/Master distinctions. Routing opens the same selected stable bus in Details. Color supplements text/state, not the only indication of mute, focus or overload.
- Keep edit cursor, selected range, playback row and keyboard focus visually distinct. Show Live keys/Record arm continuously. Highlight the panel that will receive keystrokes without coloring every active control identically.
- Prefer native Edit/ComboBox/ListView/TreeView/Trackbar controls where they fit. Custom waveforms, curves, pattern grid and graph remain accelerated canvases, with native keyboard commands and UIA semantic peers. UIA patterns should cover selection, range value, invoke, scrolling and grid coordinates; expose unavailable/stale reasons.
- Ctrl+K opens command search; Ctrl+Z/Ctrl+Y and Ctrl+Shift+Z remain native editing conventions; F6/Shift+F6 cycle regions; Alt menus/mnemonics and context-menu key/Shift+F10 expose local commands. Ctrl+Space in formula editing is local completion. Text editing owns text shortcuts; musical typing owns held physical notes only in its explicit context. Do not mechanically replace every Mac modifier with Ctrl.
- An ordinary point/field edit may commit on Enter or completion of a gesture, with one Undo and inline errors. Multi-field destructive transforms/imports retain Preview/Apply. Escape cancels a draft before invoking transport stop; record and document the context precedence. No routine reversible edit needs a confirmation dialog.
- A visible dirty inspector raises its existing owner on reopen. Pin follows stable target, Follow deliberately reconnects, Return restores the captured opening context. Resize/reparent/layout restore preserves text/caret/scroll/selection and never triggers Apply. A deleted target shows unavailable and offers deliberate retargeting.
- At narrow widths, collapse low-priority details, scroll long editor content, then use an explicit compact tab layout; keep transport and Apply/Cancel/error feedback reachable. Save per-monitor floating placement and recover offscreen windows into the current work area. Extend existing regions rather than replacing docking in the Mixer batch.

Concrete additions from the peer review:

- Generate a real Win32 menu bar from the semantic command registry (File/Edit/View/Pattern/Playback/Automation/Graph/Window/Help), with Alt/F10, mnemonics, current shortcuts, checked state and disabled reasons. Palette, menu, tooltips and context menus should share availability rules. A method or button present in source is not necessarily searchable or bindable. Retain Windows shortcut aliases and migrate saved IDs without breaking user mappings.
- Add semantic theme/type/spacing tokens around `NativeControls` and `RenderSurface`, resolve high contrast from system colors, and refresh on setting/theme changes. Use the system UI font and optional tested fallbacks; no mandatory font installation. Make audio/control/note connections distinct by solid/dashed/dotted strokes, labels and port shapes as well as hue. Keep the already-distinct Windows cursor and playhead. Severity text must distinguish errors from hints.
- Audit the application manifest and common-controls version: none is supplied in the inspected resource path, while per-monitor-v2 is requested at runtime. Introduce comctl32-v6/DPI declarations as a separately qualified UI foundation slice; recalculate owner-drawn item heights on DPI changes and use measured, scrollable form layouts. Do not enable a UTF-8 active code page, change long-path policy or force rounded/titlebar effects without checking existing conversions and supported OS behavior.
- UIA scaffolding accompanies each new custom surface: tracker Grid/Table semantics and focused cell; graph nodes/routes with named relations; curve points and mixer values with RangeValue/selection; mute/solo as Toggle. Preserve stock HWND accessibility and give unlabeled edits and icon buttons explicit names. Validate keyboard tab order against visual order, including hidden controls, and use Narrator/Magnifier on a real desktop. Absence of a custom provider is a confirmed implementation gap, not a measured claim that the entire app is inaccessible.
- Target 1366×768 at 125% as an additional compact-work-area case, plus 100/150/200%, text scaling and mixed-DPI moves. This is a proposal to test against usable work area, not a promise that existing 900×620-DIP minimum fits. Floating panels should have appropriate owner/activation/Alt+Tab/Snap behavior; do not remove `WS_EX_TOOLWINDOW` from every auxiliary window indiscriminately.
- Retain current shortcut preferences while adding explicit focus-return and Stop commands. Escape first cancels the active gesture/preview, then returns focus without stopping as an accidental side effect. Do not silently remap a user's saved Escape=Stop binding. Audit AltGr and IME before choosing defaults; Ctrl+Space completion stays scoped to formula text. Gesture-end commits are the default proposal for direct manipulation; raw multi-field forms retain Preview/Apply. A stale conflict may rebase only after proving the complete operation read-set is unchanged, not merely one displayed value. “Keep mine” must revalidate a new candidate; it is never a force-write bypass.

A read-only display query reported 2880×1800. It did not establish effective DPI, largest monitor or usable work area. A16 begins with actual monitor/work-area/DPI enumeration and designs the primary layout for that environment. Minimum-window and 100/150/200% scale cases supplement, rather than replace, the user's main display.

Everyday journeys to measure are: enter a phrase → refine fractional hits → copy a repeated arrangement block; import the three Parity samples → loop/shape → map instrument → edit linked envelope; select a parameter → author formula → trace its source → return; mix buses while listening → route a send/sidechain → Undo; record a MIDI take or audio sample → review → commit → recover/save → reopen on the other platform. Record unnecessary panel switches, lost focus and pointer-only steps, not just screenshots.

## Bounded validation and main integration policy

Validation tiers are distinct: pure model/codec tests, native provider/worker tests, actual app API/UI, foreground presentation/accessibility, and device/audio measurements. Passing an earlier tier does not establish a later tier.

Before a batch, record baseline commit, dependency/source hashes, compiler/SDK/architecture/options, executable hash, plugin module hashes, fixtures and construction parameters. Review static diffs and run cheap deterministic tests during authoring; freeze the cohesive candidate before the expensive app build. Reuse the built executable for all targeted scenarios that do not change its inputs. Avoid rebuilding for report or screenshot annotations.

Existing entry points are `windows/build.ps1`, `windows/CMakeLists.txt`, `windows/cmake/PortableTests.cmake`, `windows/Tests/run_isolated.py`, `mac/build.sh`, `mac/CMakeLists.txt`, `mac/test-interface.sh`, `mac/Tests/test_automation.py`, and separate Mac startup/recovery/shutdown scripts. Tests in separate Windows subprojects such as `Tests/Editing`, API and provider projects are not automatically included in the main CTest count; include the applicable targets explicitly. During implementation, enumerate registered tests and use anchored targeted names with `--no-tests=error`; never treat a filter that selected zero tests as a pass.

Example future Windows sequence: build one dedicated Release directory without `-Test` while iterating; run focused CTest targets and `run_isolated.py --test <module>` with `SCREAMSEQ_TEST_EXE` pointing at that exact executable and a new absolute log path. At the batch boundary, run its required target set once. The final gate uses `-Test`/full CTest and full isolated app suite. Equivalent Mac workflow uses a dedicated development bundle/build directory and targeted CTest before the final full gate. These are instructions for future implementation; none were executed for this plan.

Broader validation is triggered by changes to shared document history/allocator, codecs, engine timing/voices, host publication, build/link inputs, common event dispatch/owner lifetimes, or failures outside the intended slice. `soundlib` changes additionally need stock OpenMPT PCM comparisons at multiple rates/block sizes and preservation of `OPENMPT_EDITOR_CORE` guards. Device/provider/adoption changes require callback safety audit; sanitizer success alone is insufficient. Pure color/layout edits need native UI/accessibility checks, not repeated whole-engine PCM suites.

Evidence reuse requires **all relevant transitive inputs** unchanged: code, build options/toolchain, fixture, platform/architecture/provider and scenario. Hash equality of one source file or an old report date is insufficient. Mark reused evidence explicitly with its original identity and scope; do not relabel its capture date. Retain failed attempts and their diagnoses. Never relax thresholds, assertions, test fixture semantics or unsupported-case reporting to save time.

P0c guardrails should be narrowly useful: a typed fixture comparator, an API inventory/exception ratchet, and a declared-vs-scheduled test inventory. Publish the generated reference fixtures/WAVs with hashes and provenance in a small repository test corpus; retain gallery/screenshots as external immutable evidence. Verify redistribution/provenance rather than importing arbitrary user songs. Use standard-library tooling for fixture normalization where practical. Compare booleans, integers and reals as distinct types, exact integer values, float bits for serialization invariants, dictionary keys without order and arrays with order; binary data compares exact bytes or length plus cryptographic hash. The supplied Python property-tree equality is useful evidence but does not distinguish `True`, `1` and `1.0`.

Differential corpus additions: effect=0/parameter>0 precise notes; missing non-nudge duration; unknown fields at root/record/identity-array positions; duplicate/reordered/deleted identities; future versions; retained missing AU/VST3 state; malformed required versus recoverable optional fields; supplementary-plane UTF-8 and invalid encodings; finite integer-valued reals, booleans, fractions and safe-range boundaries. ### Reciprocal final fixture gate

For every F01–F05: Mac original → Windows open/save-as W1 → Mac open/save-as M1 → Windows reopen; then originate a Windows edit W2, reopen/edit on Mac M2 and return to Windows. No-edit legs compare **typed** property trees and exact opaque/module/sample bytes. No allocator, plugin identity or revision change is exempted by default on a no-edit leg. Edit legs compare expected musical changes and unrelated preservation; do not demand identical binary plist byte ordering or revert allocator high-water marks after Undo. Allow high-water growth only in the documented allocation/Undo scenario, not as an unrestricted normalization. Include plugin reorder/binding, precise/FX/arrangement, sample loop/PCM, linked bank, graph trim/group/port and recorded automation cases. A missing plugin must preserve state and fail preparation clearly, never silently render dry. Preserve complete evidence: before/after songs, normalized semantic comparisons, API receipts, image type, actual build, rates/buffers and limitations.

Use automated CI artifact exchange for deterministic no-edit reciprocal saves where available; retain edited UI/device journeys separately. Do not promise cross-architecture bit-identical PCM before measuring the deterministic renderer/compiler paths. First characterize float/SIMD/provider differences on unchanged builds, choose a justified strict threshold per signal/path, and preserve all existing same-host assertions. Mitigate through typed candidates, explicit ownership, differential adapters and reciprocal files rather than UI duplication.
- Performance risk comes from rebuilding controls/catalogues/graphs during draw or telemetry ticks. Keep immutable snapshots, bounded pools/queues and cached geometry. Do not infer realtime or 60fps compliance from a small gain fixture or private image.

Each has an owner phase and acceptance recipe; none is silently counted as a missing feature or a pass.
- The independently verified current-main Mac and Windows CI failures, interface harness failure and reciprocal fixture gap are explicit P0/P8 gates. They do not justify weakening checks or beginning implementation during this planning task.

No user decision blocks the recommended first batch.
